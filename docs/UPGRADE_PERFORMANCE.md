# v1.6.3 → 2.x 升级性能对照

> **一句话**：同样硬件上，游戏负载单机吞吐提升 **1.6~2.7 倍**——4 万在线时 v1.6.3 已过载倒退、2.x 仍稳定在 12.3 万事务/秒；高冲突热点场景最高 **18 倍**，脏记录只读约 **3 倍**，事务集合常驻内存省约 **27%**。无冲突的纯吞吐场景大致持平（明细见下表）。

配套阅读：[CHANGELOG.md](CHANGELOG.md)（逐版本变更）、[MIGRATION.md](MIGRATION.md)（升级操作）、[ZezeJava/BENCHMARK.md](../ZezeJava/BENCHMARK.md)（测量协议与原始档案）。

## 结论速览

| 类别 | 场景 | 变化 |
|---|---|---|
| 收益 | 游戏混合负载（在线数越高收益越大） | **1.6~2.7×** |
| 收益 | 强冲突事务（受限池口径） | **~18×**（无界形态 3.9×，见口径二） |
| 收益 | 脏记录只读事务 | **2.9×** |
| 收益 | checkpoint 合并刷盘 | 1.4× |
| 收益 | 事务集合内存 / 批量写延迟 | 驻留 **-27%** / p50 120µs→**44µs** |
| 持平 | 一般并发、容器事务、MMO 画像、Rpc 回环、派发池 | 0.87~1.05× |
| 持平 | 干净记录只读 | ~0.97× |

单机 RocksDB 用户另需注意：2.x 起主库写统一为同步刷盘（fsync 后才返回），纯写吞吐约为原来的 1/3——这是持久化语义加强的代价，详见核心微基准表的 E2 行。

## 测量口径

- **同机同日交替**（16C / Windows / JDK 21 / 4g 堆 / 断言开），v1.6.3 侧跑在与 2.x 完全同一套基准负载的回植分支 `bench/backport-v1.6.3` 上；2.x 侧为 `e4b010eec`（2.0.7-SNAPSHOT，经实测与 v2.0.6 无性能差异）。
- 每场景多轮取中位数；绝对数与机器强相关，**倍数看量级不看小数**。
- L 场景负载为 2026-10 终版形态（在线数模型、排行榜 512 分片、K=10 节奏、穿装备/全服邮件微事务），两侧对齐。唯一能力差：v1.6.3 无脏读 API（`selectDirty`），好友查询走读集校验——这本身就是升级收益的一部分。

## 游戏负载（最接近真实业务）

MMO-lite 游戏模拟：登录/战斗/背包/交易/邮件/排行/好友七类真实事务，虚拟线程玩家，窗口制测量取中位数。

| 档位 | v1.6.3 | 2.x | 倍数 |
|---|---:|---:|---:|
| 5000 在线 @K=160 | 11.5 万事务/s | 27.0 万事务/s | **2.35×** |
| 5000 在线 @K=320 | 14.5 万事务/s | 26.2 万事务/s | 1.80× |
| 20000 在线 @K=10 | 6.7 万事务/s | 10.5 万事务/s | 1.57× |
| 40000 在线 @K=10 | 4.5 万事务/s | 12.3 万事务/s | **2.71×** |

**在线压力越大差距越大**：v1.6.3 在 4 万在线时因 redo 风暴开始倒退（吞吐反而低于自己的 2 万档）；2.x 依靠纯读事务免编组、RRS 非公平锁等改进仍处在线性扩展区。K 是单玩家操作强度倍率，K 越大单个玩家的事务越密。

## 核心微基准（A~K 场景）

按各自版本基准车道的默认形态测：

| 场景 | 含义 | v1.6.3 | 2.x | 倍数 |
|---|---|---:|---:|---:|
| B 强冲突 | 20 万事务全踩同一 key | 1.40 万 | 4.9 万 | 3.9×¹ |
| H 只读·脏记录档 | 读正在被写的记录 | 33.4 万 | 96.9 万 | **2.90×** |
| E 合并刷盘 | checkpoint MultiThreadMerge | 70.6 万 | 98.6 万 | 1.40× |
| E 单线程刷盘 | checkpoint SingleThread | 8.0 万 | 8.1 万 | 1.01× |
| H 只读·干净记录档 | 读已刷盘的干净记录 | 100.8 万 | 98.1 万 | 0.97× |
| D 容器事务 | bean 内集合读写 | 60.8 万 | 53.3 万 | 0.88× |
| C 一般并发 | 5000 key 分散并发 | 91.3 万 | 83.8 万 | 0.92× |
| I MMO 画像 | 五类操作混合微负载 | 33.2 万 | 31.0 万 | 0.93× |
| J Rpc 回环 | 256B 定长网络回环 | 27.3 万 | 23.6 万 | 0.87× |
| A 单线程 | 最简单事务上限 | 172.6 万 | 148.5 万 | 0.86× |
| F 派发池 | 虚拟线程池调度 | 87.4 万 | 78.8 万 | 0.90× |
| E2 RocksDB 主库 | 真实 RocksDB 哨兵 | 47.6 万 | 17.3 万 | 0.36×² |

单位均为事务/秒（多轮中位数）。

### 如何理解小幅下降

0.86~0.97× 的行分三层看：

- **多数在噪声带内，未检出稳定回退。** 判定协议要求变化超过 3×合成标准差才作数，而 A/C/D/I 的同侧复测轮间波动达 ±17~34%（如 v1.6.3 的 A 两轮为 197.7 万/147.5 万）。按稳态值折算，这些场景实际落在约 0.9~1.05×，方向不能断言；H 干净只读就是持平。
- **确有小幅下降的是 J（Rpc 回环 0.87×）与 F（派发 0.90×）**，两侧轮间都很稳，主要对应 netty 4.1→4.2 与调度路径的语义变化，量级为个位数百分比。
- **结构性代价：简单事务为新能力支付固定检查成本。** 下降场景全是无冲突的简单路径——单字段写、容器读写、回环。2.x 的提交路径多了 History 增量、监听器注册表、Onz 协调的检查点以及更严格的计数语义，这些能力关闭时也要过分支，恰好在此类场景不发力、只付成本；它们发力之处（冲突 4~18×、脏读 2.9×、容量 1.6~2.7×、内存 -27%）都在上面的表里。真实业务是混合负载（L 场景），固定成本被冲突与容量收益淹没——四档全胜。

## 两个必须知道的口径

**¹ B 场景与线程池形态。** 历史基准默认受限虚拟线程池（JUnit 检测），2.x 自 `4f74b3e11`（2026-10-29）起统一为生产默认的**无界 VT** 形态：

| 池形态 | v1.6.3 | 2.x | 倍数 |
|---|---:|---:|---:|
| 受限池（历史档案口径） | 1.28 万 | 23.1 万 | **18×** |
| 无界 VT（生产默认） | 1.26 万 | 4.9 万 | 3.9× |

v1.6.3 两种形态几乎不变（瓶颈是每次 redo 重试都打 INFO 日志的旧实现——18× 中约一个数量级来自修复它，架构性收益约 2×）。无界形态对"20 万并发事务全踩一个 key"这种合成极端冲突本身不利；真实业务的冲突形态以上面的 L 场景为准。冲突确实极端的业务可用 `-DuseUnlimitedVirtualThread=false` 切回受限形态。

**² E2 是语义加强，不是回退。** 2.x 起主库 RocksDB 写统一改为 sync（fsync 后才返回）；v1.6.3 是进 OS 缓冲即返回。0.36× 就是 fsync 的代价，换来的是崩溃时不丢已确认事务。

## 内存与批量写（2026-10 档案数）

- 事务集合默认 ktt 后端：5000 玩家驻留堆约 **-27%**（PList 档约 -30%），冷装载耗时约 **-40%~-51%**。
- 256 条批量写 p50：120µs → **44µs**。

## 复现

```bat
rem 2.x 侧（ZezeJava 目录）
gradlew.bat :ZezeJavaTest:benchCore -PbenchTag=名称 -PbenchHeap=4g
gradlew.bat :ZezeJavaTest:benchGame -PgamePlayers=40000 -PgameK=10 -PbenchHeap=4g -PbenchTag=名称

rem v1.6.3 侧（bench/backport-v1.6.3 分支的同名车道）
gradlew.bat :ZezeJavaTest:benchCore -PbenchTag=名称 -PbenchHeap=4g -PbenchUnlimited=true
```

判定协议（同日 A/B、3×噪声门限等）与全部原始 JSON 见 [ZezeJava/BENCHMARK.md](../ZezeJava/BENCHMARK.md) 与 `ZezeJavaTest/bench-results/`（本机留存）。
